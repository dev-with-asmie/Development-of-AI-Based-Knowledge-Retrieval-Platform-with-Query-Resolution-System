# M1.1 – Research and Technical Understanding

## Project Title
**Development of AI-Based Knowledge Retrieval Platform with Query Resolution System**

## 1. Introduction

The objective of this project is to develop an AI-based knowledge retrieval platform that allows users to upload documents and ask questions using natural language. The platform retrieves relevant information from uploaded documents and generates context-aware responses using Retrieval-Augmented Generation (RAG).

The system will also incorporate a multi-agent query resolution mechanism to understand user queries, retrieve relevant information, generate responses, clarify ambiguous questions, and maintain conversational context.

This document presents the research and technical understanding required before implementing the system.

## 2. Retrieval-Augmented Generation (RAG)

### 2.1 What is RAG?

Retrieval-Augmented Generation (RAG) is an AI technique that combines information retrieval with Large Language Models (LLMs).

Instead of depending only on the knowledge learned during model training, a RAG system retrieves relevant information from an external knowledge source and provides it to the LLM as context.

This helps generate responses that are more relevant to the user's documents and reduces the chances of unsupported answers.

### 2.2 Why is RAG Required?

RAG is useful because:

- It allows the system to answer questions using user-uploaded documents.
- It provides access to information that may not be part of the LLM's training data.
- It helps reduce hallucinations by grounding responses in retrieved content.
- It can provide source references for generated answers.
- The knowledge base can be updated without retraining the LLM.

### 2.3 End-to-End RAG Pipeline

The RAG pipeline consists of two major stages.

**A. Document Ingestion Stage**

1. User uploads a document.
2. The system extracts text from the document.
3. Extracted text is cleaned and normalized.
4. Text is divided into smaller chunks.
5. Each chunk is converted into a numerical vector using an embedding model.
6. Vectors and associated metadata are stored in a vector database.

**B. Query and Retrieval Stage**

1. User submits a natural-language question.
2. The query is converted into an embedding.
3. The vector database searches for semantically similar chunks.
4. The most relevant chunks are retrieved.
5. Retrieved content is passed to the LLM as context.
6. The LLM generates an answer based on the retrieved information.
7. The response is returned to the user with relevant source information.

## 3. Document Chunking Strategies

### 3.1 What is Chunking?

Chunking is the process of dividing a large document into smaller, meaningful sections called chunks.

LLMs and embedding models work more effectively with manageable text segments. Chunking also allows the retrieval system to identify specific information rather than retrieving an entire document.

### 3.2 Common Chunking Strategies

**1. Fixed-Size Chunking**

Text is divided into chunks based on a fixed number of characters or tokens.

Advantages:
- Simple to implement.
- Provides predictable chunk sizes.

Limitation:
- May divide sentences or paragraphs in the middle.

**2. Recursive Character Chunking**

The text is divided using a hierarchy of separators, such as paragraphs, line breaks, and sentences.

Advantages:
- Attempts to preserve meaningful text boundaries.
- Suitable for general-purpose document processing.

**3. Sentence-Based Chunking**

Documents are divided into chunks containing complete sentences.

Advantages:
- Preserves sentence-level meaning.
- Useful for retrieving specific facts.

**4. Semantic Chunking**

Text is divided based on changes in meaning or topic.

Advantages:
- Attempts to preserve contextual relationships.
- Can improve retrieval quality for complex documents.

### 3.3 Proposed Chunking Approach

The initial implementation will use recursive character-based chunking.

The proposed starting configuration is:

- Chunk size: approximately 600 tokens.
- Chunk overlap: approximately 100 tokens.

Overlap allows adjacent chunks to share some content, reducing the possibility of losing context at chunk boundaries.

These values will be treated as initial parameters and adjusted after retrieval testing.

## 4. Embeddings and Semantic Similarity

### 4.1 What are Embeddings?

Embeddings are numerical representations of text.

An embedding model converts text into a vector containing numerical values. Texts with similar meanings generally have vectors that are closer together in the embedding space.

For example:

- "How can I reset my password?"
- "What are the steps to change my password?"

Although the wording differs, both sentences express a similar meaning.

An embedding model can represent their semantic similarity numerically.

### 4.2 Semantic Similarity

Semantic similarity measures how closely two pieces of text are related in meaning.

It helps the retrieval system find relevant information even when the user's query does not contain the exact words present in a document.

### 4.3 Cosine Similarity

Cosine similarity is a commonly used method for measuring the similarity between two vectors.

It calculates the cosine of the angle between them.

The formula is:

Cosine Similarity(A, B) = (A · B) / (||A|| × ||B||)

A higher cosine similarity generally indicates that two vectors are more similar in direction.

### 4.4 Proposed Embedding Model

The proposed initial embedding model is:

**Sentence Transformers – all-MiniLM-L6-v2**

Reasons for selection:

- Lightweight and suitable for an initial implementation.
- Generates 384-dimensional embeddings.
- Supports semantic similarity and information retrieval.
- Can run locally without requiring a paid embedding API.

The same embedding model must be used consistently for document chunks and user queries.

## 5. Vector Databases and Vector Search

### 5.1 What is a Vector Database?

A vector database stores numerical vector representations of data and supports similarity-based searches.

In this project, document chunks will be converted into embeddings and stored in a vector database along with their metadata.

### 5.2 Vector Search

Vector search identifies stored vectors that are most similar to a query vector.

Unlike traditional keyword search, semantic vector search focuses on similarity in meaning.

### 5.3 Proposed Vector Database: Qdrant

Qdrant is an open-source vector database designed for storing and searching vector embeddings.

Reasons for selection:

- Supports similarity search.
- Supports metadata filtering.
- Provides APIs for vector storage and retrieval.
- Can be deployed locally using Docker.
- Suitable for building RAG applications.

Each stored vector will be associated with metadata such as:

- Document ID
- Chunk ID
- Document name
- Page number, where available
- Chunk text
- Upload timestamp

## 6. Multi-Agent Query Resolution

### 6.1 What is a Multi-Agent System?

A multi-agent system consists of multiple specialized AI agents that collaborate to complete a task.

Each agent is assigned a specific responsibility. An orchestration mechanism coordinates their execution and manages information flow between them.

### 6.2 Why is Multi-Agent Architecture Required?

A single LLM call may not be sufficient for a system that needs to understand queries, retrieve information, handle ambiguity, generate grounded answers, and maintain conversational context.

A multi-agent architecture separates these responsibilities into manageable components.

### 6.3 Common Multi-Agent Patterns

**1. Sequential Pattern**

Agents execute tasks in a predefined sequence. The output of one agent becomes the input of the next agent.

**2. Supervisor-Based Pattern**

A central supervisor coordinates specialized agents and decides which agent should execute the next task.

**3. Handoff Pattern**

One agent transfers control to another agent when a particular task or condition requires specialized handling.

### 6.4 Proposed Agent Architecture

The project will use a supervisor-based orchestration approach with conditional routing.

The five planned agents are:

**1. Query Understanding Agent**

Responsibilities:
- Understand the user's question.
- Identify the intent and important entities.
- Detect ambiguous or incomplete queries.
- Determine the appropriate next step.

**2. Retrieval Agent**

Responsibilities:
- Convert the query into an embedding.
- Perform semantic search in Qdrant.
- Retrieve relevant document chunks.
- Return retrieved content with metadata and similarity information.

**3. Response Generation Agent**

Responsibilities:
- Use retrieved chunks as context.
- Generate a natural-language response.
- Keep the response grounded in available information.
- Include source references where possible.

**4. Clarification Agent**

Responsibilities:
- Identify ambiguous or incomplete questions.
- Generate clarification questions.
- Obtain additional information from the user before retrieval when necessary.

**5. Conversation Memory Agent**

Responsibilities:
- Maintain relevant conversational context.
- Store or retrieve previous interaction information.
- Support follow-up questions.
- Provide contextual information to other agents.

### 6.5 Proposed Orchestration Workflow

The proposed workflow is:

1. The user submits a question.
2. The Query Understanding Agent analyzes it.
3. If the question is ambiguous, the Clarification Agent requests more information.
4. The Conversation Memory Agent provides relevant previous context.
5. The Retrieval Agent searches the knowledge base.
6. The Response Generation Agent generates a grounded answer.
7. The response is returned to the user.

The orchestration layer will manage the execution order and conditional transitions between agents.

### 6.6 Proposed Orchestration Framework: LangGraph

LangGraph is a framework for building stateful, multi-step agent workflows.

It supports:
- Graph-based workflow design.
- Conditional routing.
- Shared state between workflow nodes.
- Multi-agent coordination.
- Controlled execution of complex workflows.

It is proposed for implementing the agent orchestration layer.

## 7. Web Speech API

### 7.1 Introduction

The Web Speech API is a browser technology that enables speech recognition and speech synthesis.

It can provide voice-based interaction in web applications.

### 7.2 Speech-to-Text

Speech recognition converts spoken language into text.

The browser's SpeechRecognition interface can capture a user's speech and return recognized text.

Proposed usage:
- The user speaks a question.
- The browser converts speech into text.
- The recognized text is submitted to the backend.
- The RAG pipeline processes the query.

### 7.3 Text-to-Speech

Speech synthesis converts text into spoken output.

The SpeechSynthesis interface and SpeechSynthesisUtterance object can be used to read generated responses aloud.

Proposed usage:
- The backend generates an answer.
- The frontend receives the answer.
- The browser reads the answer aloud.

### 7.4 Limitations

- Browser support varies.
- Speech recognition may depend on browser and operating-system support.
- Some implementations may require an internet connection.
- Microphone permissions are required.
- Recognition accuracy can vary depending on accent and background noise.

## 9. Technology Selection Rationale

The proposed technologies have been selected based on their suitability for the project's requirements.

- **React.js:** Provides a component-based frontend for document uploads and conversational interaction.
- **FastAPI:** Offers a lightweight Python backend with API support.
- **Google Gemini API:** Provides an LLM for generating natural-language responses.
- **LangChain:** Supports document loading, text splitting, embeddings, and retrieval workflows.
- **LangGraph:** Supports stateful orchestration and conditional agent execution.
- **Sentence Transformers:** Provides a lightweight embedding model suitable for semantic retrieval.
- **Qdrant:** Provides vector storage and similarity search.
- **PostgreSQL:** Stores structured application and document metadata.
- **Web Speech API:** Enables browser-based voice interaction.

These choices represent the proposed initial architecture and may be adjusted based on implementation and validation results.

## 10. Initial Technical Decisions

The following decisions are proposed for the first implementation:

1. Use RAG to retrieve information from uploaded documents.
2. Support PDF, DOCX, TXT, and CSV document formats.
3. Use recursive character-based chunking as the initial chunking strategy.
4. Start with approximately 600-token chunks and 100-token overlap.
5. Use all-MiniLM-L6-v2 for generating embeddings.
6. Store vectors and associated chunk metadata in Qdrant.
7. Use PostgreSQL for structured metadata.
8. Implement five specialized agents.
9. Use LangGraph for agent orchestration.
10. Use the Web Speech API for browser-based voice interaction.

A multi-agent architecture can separate query understanding, retrieval, response generation, clarification, and memory management into distinct responsibilities.

The proposed technology stack provides the required components for implementing the ingestion pipeline, retrieval system, agent orchestration, and user interface.
